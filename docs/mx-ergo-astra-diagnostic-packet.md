## Review request

Challenge the causal interpretation below, rank plausible faults by evidence, and propose the smallest discriminating observations or controlled experiments. Evaluate whether the installed Omarchy plugin's bounded, user-triggered recovery is correct and what can actually be prevented automatically without interrupting a working mouse. Identify any concrete code or system defect supported by the evidence, but do not equate a similar upstream issue with proof. Keep the false-connected/no-input and disconnected/reconnect-failure modes separate. No state-changing commands, edits, service restarts, adapter resets, pairing changes, bond removal, or subagents are part of this review. Other work may be in progress in the same repository; do not revert it.

## Control paths and existing mitigation

- `ErgoModel.qml` gets BlueZ properties through Quickshell, selects a configured address, and has an automatic reconnect setting tied to logind wake. The 03:08 event was not a system wake; this automatic path would not necessarily fire on a spontaneous disconnect. It has no independent proof of actual pointer activity.
- The uncommitted repo and installed plugin include an explicit manual recovery button in `ErgoPanel.qml` even when BlueZ says `Connected=yes`. `ErgoModel.qml` admits only the selected paired/bonded object; on explicit click it disconnects only that object if reported connected, waits for `Connected=no`, starts its own bounded `bluetoothctl scan le` process, attempts `Connect` on the same saved object after a fresh report or short scan warm-up, and stops its own scan on completion/cancel/failure. It does not automatically pair, remove bonds, restart Bluetooth, toggle adapter power, or select a newly advertised address. It reports link status separately from whether the scan saw the saved address. See `ErgoModel.qml` around lines 197–252 and 265–492, `ErgoPanel.qml` around 475–504.
- Local repo tests, QML lint, offscreen interaction and lockscreen checks passed September 24; installed validation/lint/recovery simulation also passed after copy. The **manual plugin button has not been clicked against live BlueZ** and its real discovery ownership/cleanup is not yet field-verified. The manual `bluetoothctl` recovery is separate evidence. No tests are requested or run for this review.
- The installed `/usr/share/omarchy/bin/omarchy-bluetooth-device` `pair` path suppresses the pair result and then runs `trust`/`connect` unconditionally; the panel routes trusted records to connect rather than pair and treats `Connected` alone as completion. Source inspection demonstrates that this logic can mislabel an incomplete bond and block corrective pairing. It was not traced to a specific user click in the `…65:01` episode and does not establish the lower-level reconnect cause.
- Current UI cannot guarantee detection of false `Connected` while a mouse is merely idle: the observed BlueZ fields may be identical. Reliable input verification would need uniquely attributable fresh mouse events or a user challenge; a generic cursor move could come from another pointer. Automatic disconnect of all apparently idle links would interrupt a working mouse. The existing manual action is a safer bounded fallback.

## Astra review received 2026-09-25; coordinator source checks

The independent read-only review ranks a failure in the LE advertisement/connection-initiation path on the BlueZ–kernel–controller side as the leading **working hypothesis** for the disconnected-bond episodes, at medium confidence. It does not attribute the defect to a specific component. The false-`Connected` episodes require their own HID/input-path measurement. Other live possibilities are mouse reconnect advertising mode, host identity/resolving-list mismatch, USB runtime power management, and, only if connection reaches security setup, a key/encryption failure. The temporary all-device scan silence and the direct-fail/scan-success sequence strengthen the first hypothesis but do not prove it. The reviewer agreed that #2503 is only analogous.

The review sharpened two interpretations: displayed addresses beginning `C2` have the **static random** bit pattern, so their successive values should not be called proven rotating privacy addresses; the on-air address can still differ from BlueZ's saved identity. Also, no new `bluetoothctl` output is not equivalent to no HCI advertising reports. At the next failure, collect adapter discovery state, scan/filter behavior, mouse LED/channel, selected address, BlueZ flags and input registration *before* any reset or new pairing. A synchronized HCI trace, if permissions are separately available, is needed to distinguish failed report delivery, connection initiation, encryption and later HID delivery. For `Connected=yes` with a registered input node, a short, uniquely attributed MX Ergo input-event observation is more discriminating than immediately repeating pairing.

The reviewer found two concrete **plugin control-flow defects**, confirmed against `ErgoModel.qml` and [Quickshell 0.3.1 BluetoothDevice implementation](https://github.com/quickshell-mirror/quickshell/blob/v0.3.1/src/bluetooth/device.cpp):

1. `startRecoveryConnect()` calls `BluetoothDevice.connect()`, but `cancelRecovery()` / `finishRecovery()` stop only the scan process and clear the UI attempt. A pending D-Bus `Connect` may continue and finish later. The UI can therefore say `cancelled` or `timeout` and admit a new attempt while the original connection is in flight. Quickshell's `BluetoothDevice.disconnect()` returns immediately when its `Connected` flag is false, so it is not a reliable cancellation of a pending connect. [BlueZ Device API](https://github.com/bluez/bluez/blob/5.87/doc/org.bluez.Device.rst) says a direct `Device1.Disconnect()` can cancel a preceding `Connect`. The existing cancellation simulation checks only cancellation **before** `Connect`.
2. The automatic wake path clears its local `isConnecting` flag after eight seconds and schedules a second call after ten seconds, but Quickshell refuses another `connect()` while its device state remains `Connecting`. On a long first attempt, the apparent second retry may do nothing. This wake-only defect does not explain the overnight event without suspend.

These were findings for the next implementation pass, **not fixes applied by Astra's review**. The review found no source-level reason to think terminating this plugin's own `bluetoothctl` discovery client stops another client's session. Discovery still uses a shared radio and can affect scheduling. No tests or Bluetooth state-changing operations were performed for this review. The later live results are recorded below.

The journal line lacks a device address. Which device and return path produced the host's errors, and whether they caused the earlier failure, are still unknown. This supports measuring the HID handoff as well as the LE connection path on the next recurrence.

The subsequent repository and installed plugin now include a single bounded startup attempt when a selected bonded record is disconnected; it has passed local tests and shell-load checks, but not a future cold-boot field test.
